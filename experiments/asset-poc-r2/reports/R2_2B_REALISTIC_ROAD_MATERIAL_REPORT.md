## Research on reusable approaches

- [CARLA RoadPainter and M_RoadMaster](https://carla-ue5.readthedocs.io/en/latest/content_authoring_maps_road_painter/) describe base color/normal/roughness plus optional second base, macro variation, wheel marks and patch layers, and painted masks. The current CARLA documentation also warns of a shared hard-coded render target; that limitation is specific to its implementation. Adopt layered and authored-mask concepts, not CARLA assets or an Unreal shader. CARLA's [materials guidance](https://carla-ue5.readthedocs.io/en/latest/content_authoring_materials/) also describes wetness behavior; this experiment targets dry road.
- [Epic detail textures](https://dev.epicgames.com/documentation/en-us/unreal-engine/adding-detail-textures-to-unreal-engine-materials) illustrate distance-dependent blending and warn that extra texture lookups cost mobile resources. Fading a contribution is not necessarily the same as skipping its sample; measure actual shader and hardware before claiming a speedup.
- [three-hex-tiling](https://github.com/Ameobea/three-hex-tiling) has an MIT project license, extends standard PBR maps, and describes up to 3 fetches per map. It patches Three.js globally and documents testing only 0.151–0.173; compatibility with this repository's vendored build is unverified. Its upstream shader attribution also needs a reuse review. No code is copied or dependency installed. Compare its visual benefit and GPU cost in isolation before adoption; 3 maps could imply up to 9 texture fetches rather than 3.
- [Mikkelsen hex-tiling demo](https://github.com/mmikk/hextile-demo) is MIT-licensed reference code and discusses precision-aware coordinates, but is not a drop-in Three.js/WebGL package. License is not a performance guarantee. [ovsky stochastic sampler](https://github.com/ovsky/stochastic-texture-sampling) asks for Three.js porting and does not expose a clear license in the reviewed page; reject code reuse until license and compatibility are established. No external shader code has been incorporated.
- Other candidates: deterministic per-cell transforms can introduce seams and normal handedness problems; texture bombing and multi-sample stochastic blending can hide repetition but cost bandwidth; sparse authored decals add draws/overdraw and should not be spawned randomly per frame. KTX2/Basis may lower GPU memory/bandwidth on supported formats but entails transcoding, capability selection and validation; defer a pipeline until device evidence justifies it.

## Chosen architecture for next checkpoints

**A — baseline**: existing CC0 [Poly Haven Asphalt Track](https://polyhaven.com/a/asphalt_track), original 1K diffuse/GL normal/roughness JPGs and manifest in `assets/asphalt-track/`; source author Dimitrios Savva, [CC0](https://polyhaven.com/license), nominal 2 m source repeat. One standard PBR material, metalness zero. The checkpoint adds `road/road-surface.mjs`, a reusable baseline factory with explicit color spaces, repeat, mip and filtering. It does not invent a calibrated roughness or repair the dark/tiling problem. It mutates the supplied texture instances: use separate clones for different repeats or phase, and clamp requested anisotropy to the renderer's device limit before calling.

**B — lightweight candidate (design, not implemented):** preserve the scanned 2 m PBR layer, evaluate a deterministic macro mask/modulation and a low-sample anti-repeat method with restrained contrast against the identical baseline. Determine macro scale by reference comparison rather than claiming a measured value; broad variation should be irregular and not mask/multiply an obvious 2 m periodic pattern with a new one. Assess whether the technique actually removes repeating structure before selecting it. Use deterministic road coordinates and retain Three.js standard lighting via an isolated, version-checked shader extension only if a standard-material solution is insufficient. Avoid global monkey-patching; test shader compile, maps and output against the vendored Three.js. Source transforms and gradients must agree across color, roughness and normal maps; rotated/mirrored normals need correct tangent-space transformation.

**C — optional wear/repair (design, not implemented):** masks from lane ID, lane width and centerline-relative distance; subtle continuous wheel corridors modulated by longitudinally coherent age and local context, not black paint. Sparse deterministic repair/resurfacing segments should be authored or seeded in a road data layer, with transition lengths and probabilities approved from references, rather than uniform arbitrary per-pixel cracks. Shoulder transitions derive from road metadata. Draw calls, samples and quality must justify keeping C; B must remain usable separately.

Distance control should attenuate micro-detail smoothly with screen footprint and be tested in motion, while preserving consistent roughness/normal energy. 2 m scan scale is documented by the source, not a measurement from road photos. Larger age zones, lane widths, wear amplitudes, fade distances and repair frequency are **not yet calibrated**. Test sensitivity instead of asserting invented reference-derived numbers. Prevent repeating macro periods with independently seeded long segments and overlap continuity, not raw floating world positions. Chunk boundaries require shared stable road coordinates and deterministic metadata, with origin rebasing preserving phase. Baseline helper computes a bounded texture phase from an integer millimetre BigInt start; its unit tests cover sign and very large offsets. This proves arithmetic only, not GPU or curved-road continuity. Seamless macro masks, lane coordinates and transitions remain future work.
